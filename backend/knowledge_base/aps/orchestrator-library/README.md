**版本**: v1.0

**模块**: BMAD APS (Advanced Planning & Scheduling)

## 📋 知识库概述

### 知识库定位

系统编排专家知识库是 BMAD APS 模块中专门负责多智能体协作编排、决策策略、方案融合和风险控制的知识集合,是实现智能体团队高效协作的核心知识库。

**核心价值**:

- 提供智能体协作的编排模式和决策框架
- 封装专家选择、冲突解决、质量评估的策略知识
- 支持串行、并行、混合等多种协作模式
- 指导系统编排智能体进行全局优化和风险控制

**使用场景**:

- 复杂调度问题的多智能体协作
- 专家智能体的选择和调度
- 多方案的融合和一致性保证
- 系统风险识别和控制

## 🗂️ 知识结构

### 一级分类:编排能力

```yaml
编排知识分类:
  1. 决策策略 (Decision Strategies):
    - 专家选择: 根据问题特征选择合适的专家智能体
    - 复杂度评估: 评估问题复杂度,确定求解策略
    - 冲突解决: 处理多专家间的方案冲突
    - 质量评估: 评估方案质量,触发优化迭代

  2. 编排模式 (Collaboration Patterns):
    - 串行协作: 专家按序执行,前序输出作为后序输入
    - 并行协作: 多专家同时工作,独立输出
    - 混合协作: 串行+并行的混合模式

  3. 集成优化 (Integration Optimization):
    - 方案融合: 整合多专家的局部方案
    - 一致性保证: 确保融合方案的约束一致性
    - 迭代优化: 多轮迭代逐步改进方案质量

  4. 风险控制 (Risk Control):
    - 风险识别: 识别调度方案的潜在风险
    - 风险评估: 量化风险影响和概率
    - 风险控制策略: 制定风险缓解和应对措施
```

### 二级分类:策略类型

```yaml
策略类型:
  - 规则策略 (Rule-Based):
      特点: 基于专家经验规则
      适用: 问题特征明确,规则可穷举
      示例: 问题规模<100用精确算法,>100用启发式

  - 评分策略 (Scoring-Based):
      特点: 多维度打分,加权求和
      适用: 需要综合多因素决策
      示例: 专家选择评分 = 能力匹配度×0.4 + 历史成功率×0.3 + 响应速度×0.3

  - 学习策略 (Learning-Based):
      特点: 基于历史数据学习
      适用: 有大量历史案例
      示例: 根据历史问题-专家-效果数据训练推荐模型
```

## 🎯 编排决策矩阵

### 如何选择协作模式?

| 问题特征                 | 推荐协作模式 | 典型工作流                 |
| ------------------------ | ------------ | -------------------------- |
| 问题可分解为独立子问题   | 并行协作     | 多专家同时求解,最后聚合    |
| 问题需多阶段逐步求解     | 串行协作     | 建模→算法→验证,顺序执行    |
| 问题既有独立部分又有依赖 | 混合协作     | 并行+串行组合              |
| 问题简单,单专家可解决    | 单专家模式   | 直接调用对应专家           |
| 问题极端复杂,需多轮优化  | 迭代协作     | 多轮串行/并行协作,逐步改进 |

### 专家选择决策树

```
问题类型是什么?
├─ 车辆调度 → 调用领域专家 (vehicle领域)
│   └─ 需要算法求解 → 调用算法专家 (推荐启发式/元启发式)
│       └─ 需要约束建模 → 调用约束专家 (temporal, capacity, spatial)
│
├─ 生产调度 → 调用领域专家 (production领域)
│   └─ 需要算法求解 → 调用算法专家 (推荐精确算法/启发式)
│       └─ 需要约束建模 → 调用约束专家 (temporal, logical)
│
├─ 服务调度 → 调用领域专家 (service领域)
│   └─ 需要算法求解 → 调用算法专家 (推荐启发式)
│       └─ 需要约束建模 → 调用约束专家 (temporal, logical, business-rules)
│
└─ 通用问题 → 直接调用算法专家
    └─ 问题规模评估 → 调用复杂度评估策略
        ├─ 小规模 → 推荐精确算法
        ├─ 中等规模 → 推荐启发式算法
        └─ 大规模 → 推荐元启发式算法
```

```yaml
阶段1: 问题理解与分解
  输入: 用户需求描述

    1. 解析问题类型 (车辆/生产/服务/项目/供应链)
    2. 评估问题复杂度 (规模、约束数量、目标数量)
    3. 识别问题可分解性 (独立子问题 vs 强耦合)
```

### 2. 冲突解决机制

```yaml
冲突类型1: 约束冲突
  场景: 多个专家提出的约束相互矛盾
  示例:
    - 算法专家: "建议放松时间窗约束以获得更优解"
    - 约束专家: "时间窗约束是硬约束,不可违反"

  解决策略:
    1. 区分硬约束 vs 软约束
    2. 硬约束优先级最高,不可违反
    3. 软约束可适当放松,但需业务确认

  引用: "@backend/knowledge_base/aps/orchestrator-library/decision/冲突解决策略.md"

冲突类型2: 目标冲突
  场景: 多个目标相互矛盾
  示例:
    - 成本最小化 vs 时效最快化

  解决策略:
    1. 使用多目标优化方法
    2. 明确目标优先级或权重
    3. 提供帕累托前沿供决策者选择

  引用: "@backend/knowledge_base/aps/objective-library/multi-objective/加权优化方法.md"

冲突类型3: 方案冲突
  场景: 多个专家提供的方案差异较大
  示例:
    - 专家A推荐遗传算法
    - 专家B推荐整数规划

  解决策略:
    1. 基于复杂度评估和历史经验选择
    2. 必要时运行多个算法,对比效果
    3. 建立算法选择的决策规则库

  引用: "@backend/knowledge_base/aps/orchestrator-library/decision/专家选择策略.md"
```

### 3. 质量评估与迭代

```yaml
质量评估指标:
  1. 约束满足度:
     - 硬约束违反数: 必须为0
     - 软约束违反度: 尽量最小化

  2. 目标函数值:
     - 与基准方案对比
     - 与理论下界对比 (如LP松弛)

  3. 计算效率:
     - 求解时间
     - 收敛速度

  4. 方案鲁棒性:
     - 对参数扰动的敏感性
     - 不确定性下的表现

迭代优化触发条件:
  - 条件1: 硬约束有违反 → 必须迭代
  - 条件2: 目标函数值未达到预期 → 可选迭代
  - 条件3: 风险评估发现高风险 → 建议迭代
  - 条件4: 时间预算充足 → 可选迭代

迭代策略:
  策略1: 调整算法参数
    - 增加迭代次数
    - 调整种群规模、温度参数等

  策略2: 切换算法
    - 从启发式切换到精确算法
    - 从单一算法切换到混合算法

  策略3: 问题分解
    - 将大问题分解为多个子问题
    - 分别求解后再融合

引用: "@backend/knowledge_base/aps/orchestrator-library/decision/质量评估策略.md"
引用: "@backend/knowledge_base/aps/orchestrator-library/integration/迭代优化策略.md"
```

## 📊 典型编排工作流示例

### 示例1: 生鲜配送调度问题

```yaml
问题描述:
  类型: 车辆调度
  规模: 100个订单, 10辆车
  约束: 时间窗, 容量, 温控
  目标: 最小化配送成本

编排流程:
  Step1: 复杂度评估
    - 问题规模: 中等
    - 约束复杂度: 高 (时间窗+温控)
    - 推荐策略: 启发式或元启发式算法

  Step2: 专家选择
    - 领域专家: vehicle/VRP领域适配器
    - 约束专家: temporal/时间窗约束, capacity/车辆容量约束
    - 算法专家: heuristic/构造式启发式 + meta-heuristic/遗传算法
    - 目标专家: cost/总成本目标

  Step3: 协作模式
    - 采用串行协作模式:
      1. 领域专家: 问题建模
      2. 约束专家: 约束定义
      3. 目标专家: 目标函数设计
      4. 算法专家: 求解优化
      5. 质量专家: 方案验证

  Step4: 执行监控
    - 各专家按序执行
    - 收集输出结果

  Step5: 方案融合
    - 整合各专家输出为完整方案
    - 验证约束一致性

  Step6: 质量评估
    - 约束满足度: 100% (所有硬约束满足)
    - 目标函数值: 比基准方案降低15%
    - 评估结果: 达标,无需迭代

  Step7: 风险评估
    - 识别风险: 交通拥堵可能导致超时
    - 控制措施: 预留时间缓冲,实时路况调整

  Step8: 输出方案
    - 车辆路径方案
    - 时间安排
    - 风险应对预案
```

### 示例2: 多目标生产调度问题

```yaml
问题描述:
  类型: 生产调度
  规模: 50个工件, 5台机器
  约束: 加工顺序, 机器容量
  目标: 最小化完成时间 + 最大化设备利用率

编排流程:
  Step1: 复杂度评估
    - 问题规模: 中等
    - 多目标冲突: 存在
    - 推荐策略: 多目标优化算法

  Step2: 专家选择
    - 领域专家: production/生产调度适配器
    - 约束专家: temporal/时序依赖约束, capacity/资源容量约束
    - 目标专家: time/最大完成时间目标, efficiency/资源利用率目标, multi-objective/帕累托前沿
    - 算法专家: exact/整数规划 (尝试) + meta-heuristic/遗传算法 (备选)

  Step3: 协作模式
    - 采用并行+串行混合模式:
      并行阶段: 约束专家和目标专家同时建模
      串行阶段: 领域专家 → 算法专家 → 质量专家

  Step4: 执行监控
    - 并行执行约束和目标建模
    - 串行执行问题求解和验证

  Step5: 方案融合
    - 整合多目标的帕累托前沿
    - 提供3-5个非支配解供选择

  Step6: 质量评估
    - 帕累托解验证: 确认为非支配解
    - 目标函数值: 覆盖不同权衡点
    - 评估结果: 达标

  Step7: 冲突解决
    - 识别目标冲突: 完成时间 vs 利用率
    - 解决策略: 提供多个方案,决策者根据业务优先级选择

  Step8: 输出方案
    - 3个帕累托最优方案
    - 方案对比表 (完成时间, 利用率)
    - 推荐方案及理由
```
