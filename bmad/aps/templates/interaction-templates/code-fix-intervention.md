# 交互模板: 代码修复人工介入

**模板ID**: `code-fix-intervention`
**触发级别**: P0 (关键修复失败)
**使用场景**: 自动修复失败后请求人工介入
**预计时间**: 10-20分钟（审查和决策）

## 模板目标

- 诚实报告自动修复失败的情况
- 提供详细的验证错误信息
- 说明已尝试的修复方法
- 获取用户决策：手动修复、降低标准、重新开始或终止

## 触发条件

当以下情况发生时使用此模板：

1. **代码自动修复重试2次后仍然失败**
2. **修复置信度低于50%**
3. **发现无法自动修复的错误类型**
4. **用户明确要求人工审核**

## 交互流程

### 步骤1: 报告修复失败情况

```markdown
## ⚠️ 代码自动修复失败

在自动修复生成的代码时，经过 **{retry_attempts}** 次尝试后，仍然存在验证错误。

### 📊 失败概况

**重试次数**: {retry_attempts} / 2
**最后修复方法**: {fix_strategy.strategy_type}
**修复置信度**: {fix_strategy.confidence \* 100:.0f}%

### 🔍 验证错误详情

**错误总数**: {validation_report.summary.total_errors}

**严重错误 (Critical)**:
{#for error in validation_report.critical_errors}

- [{error.type}] {error.message}
  - 位置: {error.lines if error.lines else "N/A"}
  - 严重程度: CRITICAL
    {/for}

**重要错误 (Major)**:
{#for error in validation_report.major_errors}

- [{error.type}] {error.message}
  {/for}

### 🔧 已尝试的修复方法

{#for attempt in fix_attempts}
**尝试 {attempt.number}**:

- 修复策略: {attempt.strategy}
- 修复动作: {attempt.actions}
- 结果: {attempt.result}
- 失败原因: {attempt.failure_reason}
  {/for}

---

### 💡 为什么需要人工介入？

根据V4.4架构的**验证-修复闭环设计**：

- ✅ 自动修复适用于: 常见错误、模式化问题、配置错误
- ❌ 人工介入需要: 复杂逻辑错误、设计问题、知识库缺失

当前错误已超出自动修复能力范围，需要您的专业判断。
```

### 步骤2: 提供可选方案

```markdown
## 🔄 可选解决方案

请选择以下其中一个方案：

### 方案1: 手动修复代码 ✋

**说明**:

- 我会保存当前生成的代码（即使有错误）
- 您可以手动编辑修复
- 适用于: 您熟悉代码结构，能够快速定位问题

**优势**:

- ✅ 完全控制修复过程
- ✅ 可以保留正确的部分
- ✅ 学习代码结构

**劣势**:

- ⚠️ 需要编程知识
- ⚠️ 耗时较长
- ⚠️ 可能引入新错误

**后续步骤**:

1. 保存当前代码到: {output_folder}/solver_with_errors.py
2. 打开代码文件
3. 根据验证报告修复错误
4. 手动运行验证

---

### 方案2: 降低验证标准 ⚖️

**说明**:

- 允许部分非严重错误通过
- 生成"可运行但不完美"的代码
- 适用于: 快速原型验证、概念测试

**调整标准**:

- ✅ 保持: Critical错误必须修复
- ⚠️ 放宽: Major错误转为警告
- ✅ 忽略: Minor错误

**优势**:

- ✅ 快速获得可运行代码
- ✅ 可以先测试核心逻辑
- ✅ 后续逐步优化

**劣势**:

- ⚠️ 代码质量降低
- ⚠️ 可能存在潜在问题
- ⚠️ 需要后续返工

**确认问题**:
您是否接受降低标准生成代码？（仅在快速测试场景推荐）

---

### 方案3: 返回重新生成方案 🔄

**说明**:

- 返回到 Phase 3 Step 3.1
- 重新集成专家分析
- 使用不同的策略生成方案和代码
- 适用于: 方案设计可能有问题

**重新生成范围**:

- 🔄 方案集成: 使用不同的融合策略
- 🔄 算法选择: 可能选择更简单的算法
- 🔄 代码生成: 使用更保守的模板

**优势**:

- ✅ 从根源解决问题
- ✅ 可能获得更好的方案
- ✅ 系统化重新设计

**劣势**:

- ⚠️ 耗时最长（15-20分钟）
- ⚠️ 丢失当前部分工作
- ⚠️ 不保证一定成功

---

### 方案4: 终止并保存进度 🛑

**说明**:

- 保存当前所有中间结果
- 标记为"部分完成"
- 适用于: 问题超出当前能力范围

**保存内容**:

- 📄 TenElementModel (Phase 1.5)
- 📄 专家分析结果 (Phase 2)
- 📄 方案文档 (Phase 3)
- 📄 问题代码 (Phase 3，带错误标记)
- 📄 验证报告 (详细错误信息)

**优势**:

- ✅ 保留所有工作成果
- ✅ 可以稍后继续
- ✅ 可以寻求外部帮助

**后续建议**:

1. 查看验证报告了解具体问题
2. 学习相关知识
3. 或联系技术支持
4. 稍后从 Phase 3 继续
```

### 步骤3: 收集用户决策

```markdown
## 🎯 请选择您的决策

请告诉我您希望采用哪个方案：

1️⃣ **手动修复代码** - 我将保存代码，您自己修复
2️⃣ **降低验证标准** - 允许部分错误，快速获得代码
3️⃣ **重新生成方案** - 返回Phase 3重新开始
4️⃣ **终止并保存进度** - 保存所有结果，稍后继续

**您的选择**: \_\_\_\_

**附加说明**（可选）:

---
```

### 步骤4: 确认和执行

根据用户选择执行相应操作：

**如果选择方案1（手动修复）**:

```markdown
## ✅ 已保存代码供手动修复

代码文件路径:

- 📁 {output_folder}/solver_with_errors.py
- 📁 {output_folder}/validation_report.json

修复指南:

1. 打开代码文件
2. 搜索 "# ERROR:" 注释查看错误位置
3. 参考验证报告中的建议修复
4. 修复后可运行: python solver_with_errors.py

祝您修复顺利！如有需要随时回来寻求帮助。
```

**如果选择方案2（降低标准）**:

```markdown
## ⚠️ 降低验证标准并生成代码

调整后的验证策略:

- ✅ Critical错误: 必须修复（阻断）
- ⚠️ Major错误: 转为警告（通过）
- ✅ Minor错误: 忽略（通过）

正在重新验证...
{执行降低标准的验证}
```

**如果选择方案3（重新生成）**:

```markdown
## 🔄 返回Phase 3重新生成

将执行以下操作:

1. 保留 Phase 1.5 TenElementModel（不变）
2. 保留 Phase 2 专家分析（不变）
3. 重新执行 Phase 3 方案集成
4. 使用不同的生成策略

预计时间: 15-20分钟

开始重新生成...
```

**如果选择方案4（终止）**:

````markdown
## 💾 已保存所有进度

保存位置: {output_folder}/

文件清单:

- ✅ ten_element_model.json
- ✅ expert_analyses.json
- ✅ solution_document.md
- ✅ solver_with_errors.py
- ✅ validation_report.json
- ✅ fix_attempts_log.json

状态标记: PARTIAL_COMPLETE

您可以稍后通过以下命令继续:

```bash
bmad aps --resume --from phase_3
```
````

感谢使用APS调度优化系统！

