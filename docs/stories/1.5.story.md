## Dev Notes

### 专家库架构（核心变更）

**设计理念：Agent as Doc**

原BMAD-METHOD系统采用"Agent as Doc"理念：智能体是知识的载体而非替代者。每个Agent拥有专属的Expert Library作为技能包依赖。

**专家库结构**:

```
backend/knowledge_base/aps/
├── algorithm-library/          # 算法专家知识库
│   ├── README.md              # 知识索引/决策矩阵
│   ├── greedy/                # 贪心算法
│   ├── heuristic/             # 启发式算法
│   ├── exact/                 # 精确算法
│   └── hybrid/                # 混合算法
├── constraint-library/         # 约束专家知识库
├── objective-library/          # 目标专家知识库
├── domain-library/             # 领域专家知识库
├── code-patterns-library/      # 代码模式库
├── extension-patterns-library/ # 扩展模式库
├── quality-criteria-library/   # 质量标准库
└── orchestrator-library/       # 编排知识库
```

**README.md作为知识索引**：

README.md不是知识本身，而是知识的"目录"和"决策矩阵"，描述了该专家库的能力和文件路径。示例：

```markdown
# 算法专家知识库

## 算法分类矩阵

### 按问题规模

| 规模 | 决策变量数 | 推荐算法 | 引用路径                    |
| ---- | ---------- | -------- | --------------------------- |
| 小   | < 100      | 精确算法 | @专家库/算法库/exact/\*     |
| 中   | 100-1000   | 启发式   | @专家库/算法库/heuristic/\* |
| 大   | > 1000     | 贪心算法 | @专家库/算法库/greedy/\*    |
```

**@引用机制**:

所有智能体输出必须包含@引用路径，指向其决策依据的知识文件：

```json
{
  "algorithm_recommendation": "遗传算法",
  "reference": "@专家库/算法库/heuristic/遗传算法.md",
  "rationale": "问题规模500变量，需要平衡解质量和求解时间"
}
```

### 两阶段提示词方案（核心技术）

**为什么需要两阶段？**

- LLM上下文窗口有限，不能一次性加载所有专家库知识
- 大部分知识在特定问题中不需要，动态加载更高效
- 中文模型function calling不稳定，不适合用工具调用来加载知识

**两阶段流程**:

```
Stage 1: 知识需求分析
┌─────────────────────────────────────┐
│ Input: problem_description          │
│ Expert Library Index: README.md     │
│                                     │
│ LLM Task:                           │
│ 1. 分析问题特征                      │
│ 2. 查阅README.md决策矩阵             │
│ 3. 确定需要加载的知识文件列表         │
│                                     │
│ Output (JSON):                      │
│ {                                   │
│   "knowledge_needed": [             │
│     "algorithm-library/heuristic/遗传算法.md", │
│     "algorithm-library/greedy/priority-based.md" │
│   ],                                │
│   "reasoning": "..."                │
│ }                                   │
└─────────────────────────────────────┘
                  ↓
        Library Loader加载知识文件
                  ↓
Stage 2: 方案生成
┌─────────────────────────────────────┐
│ Input:                              │
│ - problem_description               │
│ - loaded_knowledge (文件内容)        │
│ - previous_agent_outputs            │
│                                     │
│ LLM Task:                           │
│ 1. 基于加载的知识生成方案            │
│ 2. 在输出中包含@引用路径              │
│                                     │
│ Output (JSON):                      │
│ {                                   │
│   "recommendation": "...",          │
│   "references": [                   │
│     "@专家库/算法库/heuristic/遗传算法.md" │
│   ]                                 │
│ }                                   │
└─────────────────────────────────────┘
```

**实现示例**（伪代码）:

```python
async def algorithm_expert_node_two_stage(state: WorkflowState):
    """两阶段调用示例"""
    # Stage 1: 确定需要的知识
    stage1_prompt = f"""
    分析以下问题，确定需要加载哪些算法知识文件：

    问题：{state['problem_description']}

    可用知识索引（algorithm-library/README.md）：
    {library_loader.load_library_index('algorithm-library')}

    请输出JSON：{{"knowledge_needed": [...], "reasoning": "..."}}
    """

    stage1_response = await llm.ainvoke(stage1_prompt)
    knowledge_needed = json.loads(stage1_response.content)

    # Library Loader加载知识文件
    loaded_knowledge = {}
    for file_path in knowledge_needed['knowledge_needed']:
        content = library_loader.load_knowledge_file(file_path)
        loaded_knowledge[file_path] = content

    # Stage 2: 基于知识生成方案
    stage2_prompt = f"""
    基于以下知识，为问题推荐算法：

    问题：{state['problem_description']}

    已加载的知识：
    {json.dumps(loaded_knowledge, ensure_ascii=False, indent=2)}

    请输出JSON，包含recommendation和references字段
    """

    stage2_response = await llm.ainvoke(stage2_prompt)
    output = json.loads(stage2_response.content)

    return {"algorithm_output": output}
```

### 架构上下文

本Story实现的是BMAD-METHOD的核心工作流引擎，负责编排八大智能体的协作流程，同时迁移原系统的完整专家库体系，这是整个系统的"大脑"和"知识库"。

**组件定义** [Source: architecture/components.md#langgraph-workflow-engine]

- **职责**: 编排BMAD八大智能体工作流，管理StateGraph状态流转和checkpoint持久化
- **实现位置**: `backend/app/core/langgraph/`
- **关键接口**:
  - `create_workflow(input_data)` - 创建新工作流
  - `resume_workflow(thread_id, user_input)` - 恢复暂停的工作流
  - `interrupt_workflow(thread_id, approval_point)` - 暂停工作流等待人工确认

### 八大智能体定义

根据BMAD-METHOD V4.4.1架构，工作流包含以下八大智能体：[Source: architecture/high-level-architecture.md]

1. **Orchestrator（编排智能体）**
   - Phase 0执行
   - 职责：分析问题，规划整体工作流，分配任务给专家智能体
   - 输出：工作流规划、任务分配方案

2. **Algorithm Expert（算法专家）**
   - Phase 1执行
   - 职责：推荐和选择适合的算法
   - 输出：算法推荐列表、选择理由
   - P1确认点：用户确认算法选择

3. **Constraint Expert（约束专家）**
   - Phase 1执行
   - 职责：识别和分析约束条件
   - 输出：约束列表、约束验证规则

4. **Objective Expert（目标专家）**
   - Phase 1执行
   - 职责：定义优化目标和成功指标
   - 输出：目标函数定义、KPI指标

5. **Domain Expert（领域专家）**
   - Phase 2执行
   - 职责：提供领域知识和最佳实践
   - 输出：领域特定建议、参考资料

6. **Code Implementation Expert（代码实现专家）**
   - Phase 3执行
   - 职责：生成可执行代码，支持十要素建模
   - 输出：Python代码、单元测试
   - P2.5确认点：代码质量审查

7. **Extension Expert（扩展专家）**
   - Phase 3执行
   - 职责：分析代码扩展性，提供改进建议
   - 输出：扩展建议、重构方案

8. **Quality Expert（质量专家）**
   - Phase 4执行
   - 职责：评估整体质量，验证完整性
   - 输出：质量报告、改进建议

### Phase流转逻辑

**Phase定义** [Source: docs/langgraph集成方案.md + architecture/core-workflows.md]:

- **Phase 0**: 问题分析和工作流规划（Orchestrator）
- **Phase 1**: 算法选择和约束分析（Algorithm + Constraint + Objective）→ P1人工确认
- **Phase 2**: 领域知识集成（Domain Expert）→ P2冲突仲裁（如需要）
- **Phase 3**: 代码生成和扩展性分析（Code Implementation + Extension）→ P2.5代码审查
- **Phase 4**: 质量评估和验收（Quality Expert）

**条件路由规则**:

- Phase 0 → Phase 1：自动流转
- Phase 1 → P1确认点 → Phase 2：需要用户批准算法
- Phase 2 → Phase 3：自动流转（或触发P2冲突仲裁）
- Phase 3 → P2.5确认点 → Phase 4：需要代码审查
- Phase 4 → 结束：工作流完成

### StateGraph架构设计

**WorkflowState数据结构**:

```python
from typing import TypedDict, List, Dict, Any, Literal
from langgraph.graph import add_messages
from langchain_core.messages import BaseMessage

class WorkflowState(TypedDict):
    """LangGraph工作流状态"""
    # 输入数据
    problem_description: str
    domain: str
    constraints: List[str]

    # 工作流控制
    current_phase: Literal['P0', 'P1', 'P2', 'P3', 'P4']
    thread_id: str

    # 智能体输出
    orchestrator_output: Dict[str, Any]
    algorithm_output: Dict[str, Any]
    constraint_output: Dict[str, Any]
    objective_output: Dict[str, Any]
    domain_output: Dict[str, Any]
    code_output: Dict[str, Any]
    extension_output: Dict[str, Any]
    quality_output: Dict[str, Any]

    # LLM调用历史
    messages: List[BaseMessage]  # 使用add_messages reducer

    # 人工确认
    pending_approval: bool
    approval_point: str | None

    # 错误和日志
    errors: List[str]
```

**StateGraph构建示例**:

```python
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver

def create_bmad_workflow():
    """创建BMAD工作流StateGraph"""
    workflow = StateGraph(WorkflowState)

    # 添加智能体节点
    workflow.add_node("orchestrator", orchestrator_node)
    workflow.add_node("algorithm", algorithm_node)
    workflow.add_node("constraint", constraint_node)
    workflow.add_node("objective", objective_node)
    workflow.add_node("domain", domain_node)
    workflow.add_node("code_impl", code_impl_node)
    workflow.add_node("extension", extension_node)
    workflow.add_node("quality", quality_node)

    # 添加HITL节点
    workflow.add_node("p1_approval", p1_approval_node)
    workflow.add_node("p2_approval", p2_approval_node)
    workflow.add_node("p25_approval", p25_approval_node)

    # 设置开始节点
    workflow.set_entry_point("orchestrator")

    # Phase 0 → Phase 1
    workflow.add_edge("orchestrator", "algorithm")
    workflow.add_edge("algorithm", "constraint")
    workflow.add_edge("constraint", "objective")

    # Phase 1 → P1确认
    workflow.add_edge("objective", "p1_approval")

    # P1确认 → Phase 2
    workflow.add_conditional_edges(
        "p1_approval",
        route_after_p1,  # 函数：根据审批结果路由
        {
            "approved": "domain",
            "rejected": "algorithm",  # 重新生成算法
            "interrupt": END  # 等待用户输入
        }
    )

    # Phase 2 → Phase 3
    workflow.add_edge("domain", "code_impl")
    workflow.add_edge("code_impl", "extension")

    # Phase 3 → P2.5确认
    workflow.add_edge("extension", "p25_approval")

    # P2.5确认 → Phase 4
    workflow.add_conditional_edges(
        "p25_approval",
        route_after_p25,
        {
            "approved": "quality",
            "rejected": "code_impl",  # 重新生成代码
            "interrupt": END
        }
    )

    # Phase 4 → 结束
    workflow.add_edge("quality", END)

    # 配置PostgreSQL checkpointer
    checkpointer = PostgresSaver.from_conn_string(
        conn_string=settings.database_url
    )

    return workflow.compile(checkpointer=checkpointer)
```

### Checkpoint持久化机制

**PostgreSQL Checkpointer配置** [Source: architecture/tech-stack.md + LangGraph 0.4.1文档]:

```python
from langgraph.checkpoint.postgres import PostgresSaver
from backend.app.core.config import settings

# 初始化checkpointer
checkpointer = PostgresSaver.from_conn_string(
    conn_string=settings.database_url
)

# Checkpoint会自动保存到以下表：
# - checkpoints: 存储状态快照
# - checkpoint_blobs: 存储大型对象
# - checkpoint_writes: 存储写入日志
```

**Checkpoint使用场景**:

1. **自动保存**：每个节点执行后自动保存状态
2. **HITL暂停**：在P1/P2/P2.5确认点暂停，保存等待状态
3. **异常恢复**：模型调用失败或超时后，从最近的checkpoint恢复
4. **历史回溯**：查看工作流的完整执行历史

### HITL (Human-in-the-Loop) 实现

**中断和恢复API** [Source: architecture/components.md]:

```python
from langgraph.pregel import Pregel

async def interrupt_workflow(thread_id: str, approval_point: str):
    """暂停工作流，等待人工确认"""
    # 工作流会在下一个checkpoint自动暂停
    # 创建HumanApproval记录
    approval = HumanApproval(
        workflow_id=workflow_id,
        user_id=current_user_id,
        approval_point=approval_point,
        context_data=state_snapshot,
        decision=None  # 等待用户决策
    )
    await db.save(approval)

    return {"status": "paused", "approval_id": approval.id}

async def resume_workflow(
    thread_id: str,
    user_input: Dict[str, Any],
    config: Dict[str, Any]
):
    """恢复暂停的工作流"""
    # 从checkpoint加载状态
    workflow = create_bmad_workflow()

    # 更新状态（用户输入）
    state = await workflow.aget_state(config)
    state.values.update(user_input)

    # 继续执行
    async for event in workflow.astream(None, config):
        yield event  # 流式返回执行进度
```

### 编码标准

**错误处理**:

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(min=2, max=10))
async def call_llm_with_retry(model, prompt):
    """LLM调用失败自动重试"""
    try:
        return await model.ainvoke(prompt)
    except Exception as e:
        logger.error("llm_call_failed", error=str(e))
        raise
```

**重要约束**:

1. **性能要求**:
   - 单个智能体响应时间<10秒
   - 完整工作流执行<60分钟

   - 必须支持现有workflow.yaml配置格式
   - 不能破坏Story 1.2/1.3/1.4已实现的功能

3. **数据一致性**:
   - Checkpoint保存必须原子化
   - HITL中断点必须准确保存状态
   - 工作流恢复后状态必须一致

4. **错误处理**:
   - LLM调用失败必须有重试机制（tenacity）
   - 超时必须有明确的timeout配置
   - 异常必须记录详细日志和上下文

5. **安全考虑**:
   - 工作流执行需要用户认证（JWT）
   - 敏感数据不能记录到日志
   - Thread ID必须使用UUID防止枚举攻击

**与其他组件的依赖**:

- **Model Adapter Service** (Story 1.4): LangGraph节点通过LangChainModelAdapter调用LLM
- **Database Service**: WorkflowExecution、AgentExecution、HumanApproval数据持久化
- **API Gateway**: 通过REST API暴露工作流管理功能
- **Logging & Monitoring**: 集成structlog、Langfuse、Prometheus

**潜在风险和缓解策略**:

| 风险                             | 缓解策略                                               |
| -------------------------------- | ------------------------------------------------------ |
| LLM调用超时导致工作流卡住        | 设置30秒超时，失败自动重试3次，记录checkpoint便于恢复  |
| Checkpoint保存失败导致状态丢失   | PostgreSQL事务保证原子性，失败后回滚到上一个checkpoint |
| HITL中断点用户长时间不响应       | 设置24小时超时，自动标记为过期，发送通知提醒用户       |
| 并发执行多个工作流导致资源耗尽   | 使用信号量限制并发数（max 10），超出排队等待           |
| 智能体输出格式不一致导致解析失败 | 使用Pydantic强制校验输出格式，失败重试最多2次          |
