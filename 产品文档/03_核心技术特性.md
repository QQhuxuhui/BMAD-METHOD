# 三、核心技术特性

## 3.1 Phase 0-4 完整工作流

### Phase 0: 任务规划 (5-8分钟)

```yaml
步骤:
  0.1 需求理解与初步分析
  0.2 生成 Todo List
  0.3 用户确认 Todo List (P0级强制交互)
  0.4 初始化 TodoTracker
  0.5 💾 保存 Phase 0 状态

输出: 确认的任务清单（执行合同）
```

### Phase 0.5: 双模式交互选择 (2-3分钟)

```yaml
步骤:
  0.5.1 呈现模式A/B对比
  0.5.2 用户选择交互模式 (P0级交互)
  0.5.3 记录模式并初始化工作流
  0.5.4 💾 保存 Phase 0.5 状态

模式选择:
  模式A: 集中确认 (20-25分钟，适合专家用户)
  模式B: 增量确认 (30-40分钟，适合业务用户)
```

### Phase 1: 需求分析 (10-15分钟)

```yaml
步骤:
  1.1 深入需求理解
  1.2 TodoTracker实时追踪
  1.3 偏离检测 (相似度<0.60触发警告)
  1.4 需求澄清 (P1级交互，置信度<0.70)
  1.5 💾 保存 Phase 1 状态

输出: 结构化需求描述
```

### Phase 1.5: 十要素建模 (5-15分钟)

```yaml
步骤:
  1.5.1 构建 TenElementModel
  1.5.2 模式A: 完整确认 | 模式B: 框架确认
  1.5.3 验证十要素完整性
  1.5.4 💾 保存 Phase 1.5 状态 (关键依赖)

TenElementModel = 统一真相源
  1.决策变量  2.参数      3.约束      4.目标
  5.算法      6.时间模型  7.不确定性  8.求解配置
  9.输入数据  10.输出格式
```

### Phase 2: 专家协调 (10-48分钟)

```yaml
模式A: 4专家并行分析 (10-15分钟)
  ├─ 2.1 领域专家分析
  ├─ 2.2 约束专家分析
  ├─ 2.3 目标专家分析
  ├─ 2.4 算法专家分析
  └─ 2.5 跨专家一致性校验

模式B: 4专家串行增量确认 (31-48分钟)
  ├─ 2.1 领域专家增量确认 (5-8分钟)
  ├─ 2.2 约束专家增量确认 (10-15分钟)
  ├─ 2.3 目标专家增量确认 (8-12分钟)
  ├─ 2.4 算法专家增量确认 (5-8分钟)
  └─ 2.5 跨专家一致性校验 (3-5分钟)

输出: 专家分析报告集
```

### Phase 3: 方案集成 (15-20分钟)

```yaml
步骤:
  3.1 方案融合
  3.2 一致性检查
  3.3 生成完整代码 (Theory-to-Code)
  3.4 冲突仲裁 (P2级交互)
  3.5 用户确认最终方案
  3.6 💾 保存所有交付物到文件系统
  3.7 💾 保存 Phase 3 状态 + 交付物清单

输出: 完整解决方案 + 代码
```

### Phase 4: 质量保证 (9-12分钟)

```yaml
步骤:
  4.1 质量门禁验证
      ├─ 语法检查 (Python/YAML)
      ├─ 逻辑验证
      ├─ 约束一致性检查
      ├─ 引用完整性检查 (Guardrails)
      └─ 基准测试
  4.2 QE聚合报告 (level=pass required)
  4.3 Todo完成度检查
  4.4 交付物完整性验证
  4.5 💾 保存 Phase 4 状态

输出: 质量报告
```

**总计时间**:
- 模式A: 70-95分钟
- 模式B: 95-130分钟

## 3.2 Todo List 任务规划机制

**创新点**：将需求转化为"执行合同"，全程追踪，实时偏离检测

```yaml
机制特点:
  ✓ Phase 0 自动生成任务清单（基于需求理解）
  ✓ 用户确认形成"基线合同"（P0强制确认）
  ✓ 实时追踪执行进度
  ✓ 偏离检测：相似度 < 0.60 触发警告
  ✓ Phase 4 完成度检查：确保所有任务交付

预期效果:
  • 任务偏离率降低 67% (15% → 5%)
  • 需求理解准确度提升至 95%+
  • 用户满意度提升 25%
```

## 3.3 Human-in-the-Loop 人机协作

**5级触发规则**：在关键决策点引入人类智慧

| 级别 | 触发条件 | 示例场景 | 目标 |
|------|----------|----------|------|
| **P0** | Todo List强制要求 | • Todo确认<br/>• 十要素建模确认<br/>• 交互模式选择<br/>• 最终方案确认 | 形成执行合同 |
| **P1** | 置信度 < 0.70 | • 需求模糊<br/>• 多种可能方案<br/>• 缺少关键信息 | 澄清需求 |
| **P2** | 专家建议冲突 | • 算法选择冲突<br/>• 约束与目标矛盾<br/>• 性能与成本权衡 | 用户仲裁 |
| **P3** | 能力缺口 | • 特殊领域<br/>• 罕见约束组合<br/>• 创新性需求 | 补齐知识 |
| **P4** | 用户主动暂停 | • 需要思考<br/>• 咨询他人<br/>• 准备补充信息 | 灵活控制 |

## 3.4 Guardrails 强约束策略

**核心原则**：有据可查，杜绝幻觉，保证质量

```yaml
允许的知识来源:
  ✓ TenElementModel (十要素模型 - 统一真相源)
  ✓ @专家库/* (7大专家知识库)
  ✓ @知识模块库/* (通用知识模块)

强制要求:
  ✗ citations_required: true
    所有输出必须附@引用路径

  ✗ 禁止未经引用的推断与发挥
  ✗ 禁止超出职责边界的实现与决策
  ✗ 禁止虚构算法/约束/目标/领域规则

能力缺口处理:
  检测到缺口 → 输出"能力缺口报告"
              → 请求补齐模块或升级裁决
              → 阻断流程 (block_until_resolved)

示例:
  ✓ 正确:
    algorithm: "遗传算法"
    citation: "@专家库/算法库/meta-heuristic/遗传算法.md"

  ✗ 错误:
    algorithm: "某种进化算法"  # 无引用
    citation: null
```

## 3.5 状态持久化机制 (V4.3新增)

**解决断点续传问题**：工作流中断后可智能恢复

```yaml
持久化策略:
  • 每个Phase自动保存状态文件到磁盘
  • 保存后立即验证文件完整性
  • 保存失败阻断workflow (block_on_save_failure)
  • 支持latest链接快速访问
  • 30天清理策略，保留最新5个版本

状态文件:
  - phase_0_state.yaml (Todo基线)
  - phase_0_5_state.yaml (交互模式)
  - phase_1_state.yaml (需求分析)
  - phase_1_5_state.yaml (TenElementModel - 关键依赖)
  - phase_2_state.yaml (专家分析)
  - phase_3_state.yaml (方案+代码+交付物清单)
  - phase_4_state.yaml (质量报告)

智能恢复:
  命令: *resume
  能力:
    1. 检查当前执行状态和断点位置
    2. 验证状态文件完整性
    3. 加载上下文
    4. 从断点处继续执行
```

## 3.6 双模式交互系统

**满足不同用户群体**：专家vs业务人员

| 维度 | 模式A: 集中确认 | 模式B: 增量确认 |
|------|----------------|----------------|
| **时间** | 20-25分钟 | 30-40分钟 |
| **用户** | 专家用户 | 业务用户 |
| **特点** | 全局视角，快速高效 | 渐进式，上下文丰富 |
| **Phase 1.5** | 一次性确认完整TenElementModel | 仅确认框架(类型/数量/名称) |
| **Phase 2** | 4专家并行分析 (10-15分钟) | 4专家串行增量确认 (31-48分钟) |
| **适用** | 需求清晰，经验丰富 | 需求探索，需要引导 |
