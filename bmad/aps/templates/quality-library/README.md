## 📋 知识库概述

### 知识库定位

质量评估专家知识库是 BMAD APS 模块中专门负责方案质量验证、性能评测、代码检查和报告聚合的知识集合,确保调度方案的正确性、性能和可维护性。

**核心价值**:

- 提供多层次的质量评估机制和检查工具
- 封装语法检查、逻辑验证、约束一致性检查的规则
- 支持基准评测和性能对比分析
- 指导智能体生成高质量、可验证的调度方案

**使用场景**:

- 调度方案的约束满足性验证
- 生成代码的语法和逻辑检查
- 方案性能的基准评测
- 质量报告的生成和聚合

## 🗂️ 知识结构

### 一级分类:质量评估维度

```yaml
质量评估分类:
  1. 语法检查 (Syntax Checking):
    - Python语法检查: 确保生成代码符合Python语法规范
    - YAML/JSON语法检查: 验证配置文件格式正确性
    - 代码风格检查: PEP8, 命名规范
    - 特点: 静态检查,快速执行

  2. 逻辑验证 (Logic Validation):
    - 逻辑一致性: 检查推理过程的逻辑正确性
    - 数据流验证: 验证输入输出的数据流合理性
    - 边界条件测试: 极端情况下的行为验证
    - 特点: 深层验证,需要领域知识

  3. 约束一致性 (Consistency Checking):
    - 硬约束验证: 确保所有硬约束被满足
    - 软约束检查: 评估软约束的违反程度
    - 约束冲突检测: 识别相互矛盾的约束
    - 特点: 核心质量保障,必须通过

  4. 基准评测 (Benchmark):
    - 性能测试: 评估算法求解时间、收敛速度
    - 解质量评估: 对比目标函数值与基准方案
    - 可扩展性测试: 不同规模问题的性能表现
    - 特点: 量化评估,提供客观指标

  5. 报告聚合 (Report Aggregation):
    - 质量报告生成: 汇总各项检查结果
    - 问题优先级排序: 识别关键问题
    - 改进建议输出: 提供优化建议
    - 特点: 综合性,面向决策
```

### 二级分类:检查类型

```yaml
检查类型:
  - 静态检查 (Static Check):
      方式: 不执行代码,分析源代码
      工具: AST解析, 模式匹配, 规则引擎
      示例: 语法检查, 代码风格检查
      优点: 快速, 覆盖广
      缺点: 无法检测运行时问题

  - 动态检查 (Dynamic Check):
      方式: 执行代码或模拟执行
      工具: 单元测试, 集成测试, 仿真
      示例: 约束满足性验证, 性能评测
      优点: 准确, 发现运行时问题
      缺点: 慢, 需要测试数据

  - 混合检查 (Hybrid Check):
      方式: 结合静态和动态检查
      示例: 逻辑验证 (静态分析+运行验证)
      优点: 兼顾效率和准确性
```

## 🎯 质量评估流程

### 五层质量保障体系

```yaml
Layer 1: 语法层 (Syntax Layer)
  目标: 确保代码可运行
  检查项:
    - Python语法正确性
    - 变量命名规范
    - 导入语句完整性
    - 缩进和格式一致性

  工具: Python AST解析器, Pylint
  引用: "@专家库/quality库/syntax/Python语法检查器.md"

  通过标准: 无语法错误, 代码可执行

Layer 2: 逻辑层 (Logic Layer)
  目标: 确保代码逻辑正确
  检查项:
    - 函数输入输出类型匹配
    - 数据流完整性
    - 异常处理覆盖
    - 边界条件处理

  工具: 类型检查, 数据流分析
  引用: "@专家库/quality库/logic/逻辑验证器.md"

  通过标准: 逻辑自洽, 无明显漏洞

Layer 3: 约束层 (Constraint Layer)
  目标: 确保方案满足约束
  检查项:
    - 硬约束满足性 (必须100%满足)
    - 软约束违反度 (尽量最小化)
    - 约束冲突检测

  工具: 约束求解器, 可行性验证
  引用: "@专家库/quality库/consistency/约束一致性检查器.md"

  通过标准: 硬约束100%满足, 软约束违反度可接受

Layer 4: 性能层 (Performance Layer)
  目标: 确保方案达到性能目标
  检查项:
    - 目标函数值评估
    - 与基准方案对比
    - 求解时间评估
    - 可扩展性测试

  工具: 基准测试套件
  引用: "@专家库/quality库/benchmark/基准运行器.md"

  通过标准: 目标函数值满足预期, 性能可接受

Layer 5: 综合层 (Integration Layer)
  目标: 生成综合质量报告
  检查项:
    - 汇总各层检查结果
    - 识别关键问题
    - 提供改进建议
    - 评估整体质量分数

  工具: 报告聚合器
  引用: "@专家库/quality库/report/报告聚合器.md"

  输出: 质量评估报告, 质量分数, 改进建议
```

### 2. 约束验证详细流程

```yaml
硬约束验证 (必须100%满足):
  流程:
    1. 提取方案中的所有决策变量取值
    2. 逐条验证每个硬约束
    3. 记录违反的约束及违反程度

  示例:
    约束1: 每个工件必须分配给恰好一台机器
      验证: Σ_j x_ij == 1, ∀i
      结果: ✓ 满足 (15/15工件)

    约束2: 每台机器总加工时间不超过容量
      验证: Σ_i p_ij * x_ij <= C_j, ∀j
      结果: ✓ 满足 (5/5机器)

    约束3: 所有订单在时间窗内送达
      验证: s_i <= t_i <= e_i, ∀i
      结果: ✗ 违反 (订单#7: t=10:15, e=10:00, 超时15分钟)

  判定: 不通过 (存在硬约束违反,需重新优化)

软约束验证 (尽量满足):
  流程:
    1. 计算每个软约束的违反程度
    2. 加权求和得到总违反度
    3. 判断是否在可接受范围内

  示例:
    软约束1: 优先使用固定司机
      违反度: 2个订单使用临时司机 (目标0个)
      权重: 0.3
      加权违反度: 2 × 0.3 = 0.6

    软约束2: 负载均衡
      违反度: 最大负载差异15%
      权重: 0.5
      加权违反度: 0.15 × 0.5 = 0.075

    总违反度: 0.6 + 0.075 = 0.675
    阈值: 1.0
    判定: 通过 (在可接受范围内)
```

### 3. 性能评测指标体系

```yaml
解质量指标:
  - 目标函数值:
      含义: 方案的优化目标达成情况
      计算: f(solution)
      基准: 与已知最优解或基准算法对比
      示例: 成本4250元 (基准4680元, 改进9.2%)

  - 约束满足度:
      含义: 方案的可行性
      计算: (满足的约束数 / 总约束数) × 100%
      基准: 100% (硬约束必须)
      示例: 硬约束100%, 软约束97.7%

  - 解的鲁棒性:
      含义: 方案对参数扰动的稳定性
      计算: 参数±10%变化时目标函数值波动
      基准: 波动<5%为鲁棒
      示例: 参数扰动±10%, 目标波动±3.2% (鲁棒)

计算效率指标:
  - 求解时间:
      含义: 算法运行时长
      计算: 从开始到输出方案的时间
      基准: 实际业务时间要求
      示例: 0.8秒 (要求<5秒, 满足)

  - 收敛速度:
      含义: 达到目标解质量的迭代次数
      计算: 达到95%最优解的迭代数
      基准: 迭代次数越少越好
      示例: 50次迭代达到95%最优 (总100次)

  - 可扩展性:
      含义: 问题规模增加时性能变化
      计算: 不同规模的求解时间曲线
      基准: 时间复杂度理论值
      示例: O(n²)实际, O(n²)理论 (吻合)

算法稳定性指标:
  - 多次运行一致性:
      含义: 多次运行结果的稳定性
      计算: 10次运行目标函数值的标准差
      基准: 标准差<均值的5%
      示例: 均值4250, 标准差85 (2%, 稳定)

  - 不同初始解表现:
      含义: 对初始解的敏感性
      计算: 随机初始解的结果分布
      基准: 结果波动<10%
      示例: 最好4200, 最差4380 (波动4.2%, 良好)
```

- [ ] **可扩展性**: 能处理更大规模问题
