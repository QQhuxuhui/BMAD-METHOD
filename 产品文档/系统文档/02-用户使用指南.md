## 🚀 开始使用

### 前置条件

1. **环境准备**
   - 已安装 BMAD-METHOD 框架
   - APS 模块已正确配置

2. **问题准备**
   - 明确你的调度问题类型（车辆路径、生产排程、人员排班等）
   - 准备好业务需求描述
   - 了解关键约束和目标

### 激活 APS 模块

```bash
# 方式1: 直接激活编排器
bmad aps

# 方式2: 调用系统编排协调智能体
bmad orchestrator
```

### 启动完整求解流程

```bash
# 激活后，选择命令
*start-scheduling

# 系统将引导你完成 Phase 0-4
```

## 📋 完整需求分析流程

### 流程概览

APS 模块通过 **5个 Phase** 完成从需求到交付的完整流程：

```
Phase 0: 任务规划
    ↓
Phase 0.5: 模式选择
    ↓
Phase 1: 需求分析
    ↓
Phase 1.5: 十要素建模
    ↓
Phase 2: 专家协调
    ↓
Phase 3: 方案集成与代码生成
    ↓
Phase 4: 质量保证
```

### Phase 0: 任务规划 (5-8分钟)

**目标**: 理解你的需求，生成执行计划

**系统会做什么**:
1. 分析你的需求描述
2. 识别问题类型和关键要素
3. 生成 Todo List（任务清单）
4. 估算时间和复杂度

**你需要做什么**:
- 用自然语言描述你的调度问题
- 提供关键信息：
  - 调度对象（车辆、订单、人员等）
  - 主要约束（时间窗、容量、优先级等）
  - 优化目标（成本最小、时间最短等）

**示例输入**:
```
我们是一家生鲜配送公司，需要优化配送路线。有20辆冷藏车，
每天需要配送约200个订单到不同客户。每个客户有时间窗要求，
车辆有容量限制。我们希望最小化总配送成本，同时保证准时率。
```

**系统输出**:
```
📋 Todo List (请确认)

1. ✅ 识别领域：车辆路径问题（VRP + 时间窗）
2. ✅ 提取约束：
   - 车辆容量约束
   - 客户时间窗约束
   - 车辆数量约束（20辆）
3. ✅ 识别目标：
   - 主要：总配送成本最小化
   - 次要：准时率最大化
4. ✅ 推荐算法：遗传算法或禁忌搜索
5. ✅ 建立十要素模型
6. ✅ 生成可执行代码
7. ✅ 质量验证

预计完成时间: 70-95分钟（模式A）或 95-130分钟（模式B）

是否确认？(Y/N)
```

**关键决策点** ⭐:
- **P0触发**: 必须确认 Todo List
- 这是"执行合同"，系统会跟踪执行偏离

### Phase 0.5: 双模式交互选择 (2-3分钟)

**目标**: 选择适合你的交互模式

**系统会做什么**:
1. 呈现两种模式的对比
2. 根据你的背景推荐模式

**你需要做什么**:
- 选择模式A或模式B（详见 [双模式选择指南](#双模式选择指南)）

**系统输出**:
```
🎯 请选择交互模式

┌─────────────────────────────────────────────────────────┐
│ 模式A: 集中确认模式（推荐给专家用户）                    │
├─────────────────────────────────────────────────────────┤
│ • 特点: 快速高效，全局视角                              │
│ • 时间: 20-25分钟（用户交互时间）                       │
│ • 适合: 熟悉调度问题，能快速理解技术概念                │
│ • 流程: Phase 1.5一次性确认完整十要素模型               │
│         Phase 2 所有专家并行分析                        │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ 模式B: 增量确认模式（推荐给业务用户）                    │
├─────────────────────────────────────────────────────────┤
│ • 特点: 渐进式，上下文丰富                              │
│ • 时间: 30-40分钟（用户交互时间）                       │
│ • 适合: 关注业务细节，需要逐步理解技术方案              │
│ • 流程: Phase 1.5仅确认框架                             │
│         Phase 2 分阶段确认（领域→约束→目标→算法）       │
└─────────────────────────────────────────────────────────┘

你的选择: (A/B)
```

**关键决策点** ⭐:
- **P0触发**: 必须选择模式
- 选择后不可更改（整个流程保持一致）

### Phase 1: 需求分析 (10-15分钟)

**目标**: 深度理解和澄清需求

**系统会做什么**:
1. 深度分析你的需求
2. 识别模糊点和不确定项
3. 提出澄清问题（如需要）
4. 检测需求偏离

**你需要做什么**:
- 回答澄清问题（如触发P1）
- 提供补充信息

**可能的澄清问题** (P1触发):
```
🤔 需求澄清

我对以下几点需要确认：

1. 时间窗约束：
   - 客户时间窗是硬约束还是软约束？
   - 违反时间窗的惩罚是什么？

2. 车辆容量：
   - 容量指重量、体积还是订单数量？
   - 是否允许超载（软约束）？

3. 冷藏温度：
   - 是否有不同温区要求？
   - 混载规则是什么？

请提供补充信息。
```

**你的回答示例**:
```
1. 时间窗是硬约束，必须在客户要求的时间范围内送达
2. 容量指重量和体积两个维度，都不能超载
3. 有三个温区（-18℃, 0-4℃, 常温），不同温区不能混载
```

### Phase 1.5: 十要素建模

**目标**: 构建统一真相源 (TenElementModel)

#### 模式A流程 (10-15分钟)

**系统会做什么**:
1. 构建完整的十要素模型草稿
2. 一次性展示给你确认

**你需要做什么**:
- 审阅完整的十要素模型
- 确认或修改每个要素

**系统输出示例**:
```yaml
📐 十要素模型（请完整确认）

1. 决策变量:
   - route[v]: 车辆v的路径序列
   - service_time[v,c]: 车辆v服务客户c的时间

2. 参数:
   - vehicles: 20辆冷藏车
   - customers: 200个配送点
   - distance_matrix: 距离矩阵
   - time_windows: 客户时间窗
   - capacity_weight: [5000kg, 5000kg, ...]
   - capacity_volume: [30m³, 30m³, ...]

3. 约束:
   - 车辆容量约束 (@专家库/约束库/capacity/车辆容量约束.md)
   - 时间窗约束 (@专家库/约束库/temporal/时间窗约束.md)
   - 温区混载约束 (@专家库/约束库/business-rules/合规性约束.md)

4. 优化目标:
   - 主要: 总配送成本最小化 (@专家库/目标库/cost/总成本目标.md)
   - 次要: 准时率最大化 (@专家库/目标库/quality/服务质量目标.md)
   - 权重: 0.7 : 0.3

5. 算法:
   - 推荐: 遗传算法 (@专家库/算法库/meta-heuristic/遗传算法.md)
   - 配置: population=100, generations=500

6. 时间模型:
   - 服务时间: 每客户10分钟
   - 行驶时间: 基于距离矩阵，平均速度40km/h

7. 不确定性:
   - 订单需求波动: ±10%
   - 交通时间波动: ±20%

8. 求解配置:
   - 最大求解时间: 30分钟
   - 收敛条件: 连续50代无改进

9. 输入数据:
   - 格式: JSON
   - 来源: 订单管理系统API

10. 输出格式:
    - 路径方案: CSV
    - 可视化: HTML地图
```

**关键决策点** ⭐:
- **P0触发**: 必须确认完整模型
- 这是后续所有Phase的"统一真相源"

#### 模式B流程 (5-8分钟)

**系统会做什么**:
1. 构建十要素模型框架
2. 仅展示类型、数量、名称

**你需要做什么**:
- 确认框架结构
- 具体细节在Phase 2逐步确认

**系统输出示例**:
```yaml
📐 十要素模型框架（仅确认结构）

1. 决策变量: 2个（路径序列、服务时间）
2. 参数: 5类（车辆、客户、距离、时间窗、容量）
3. 约束: 3类（容量、时间窗、温区混载）
4. 优化目标: 2个（成本、准时率）
5. 算法: 1个（遗传算法）
6. 时间模型: 已定义
7. 不确定性: 2类（需求、交通）
8. 求解配置: 已定义
9. 输入数据: JSON格式
10. 输出格式: CSV + HTML

是否确认框架？(Y/N)
```

### Phase 2: 专家协调

#### 模式A流程 (10-15分钟)

**系统会做什么**:
1. 4个专家并行分析十要素模型
2. 生成各自的分析报告
3. 检查一致性，识别冲突
4. 如有冲突，请你仲裁

**你需要做什么**:
- 等待分析完成（系统自动）
- 如有冲突，进行仲裁（P2触发）

**可能的冲突示例** (P2触发):
```
⚠️ 专家建议冲突，需要你的仲裁

冲突点: 算法选择

🏢 领域专家 (赵领域):
   - 建议: 禁忌搜索
   - 理由: 生鲜配送行业通常使用禁忌搜索，收敛快
   - 引用: @专家库/领域库/vehicle/冷链物流最佳实践.md

⚙️ 算法专家 (张效率):
   - 建议: 遗传算法
   - 理由: 问题规模适中，遗传算法全局搜索能力更强
   - 引用: @专家库/算法库/meta-heuristic/遗传算法.md

你的选择: (1) 禁忌搜索 / (2) 遗传算法 / (3) 两者混合
```

#### 模式B流程 (31-48分钟)

**系统会做什么**:
1. 分5个阶段，逐个专家分析
2. 每个阶段请你确认

**你需要做什么**:
- 逐阶段确认专家分析结果

1. 温区管理: 三温区分离

4. 路径优化: 关键

行业最佳实践:

   - 必须在[early, late]内服务

   - 不同温区不可混载

约束处理策略:
- 容量: 装箱算法预检

## 🎚️ 双模式选择指南

### 如何选择模式？

#### 选择模式A的情况

✅ **你是专家用户，满足以下条件**:
- 熟悉调度优化领域
- 理解技术术语（约束、目标函数、算法等）
- 能快速理解完整的十要素模型
- 希望快速获得结果

✅ **你的问题特点**:
- 需求清晰，不确定性低
- 标准调度问题（VRP、Job Shop等）
- 约束和目标相对简单

⏱️ **时间投入**: 用户交互约20-25分钟，总计70-95分钟

#### 选择模式B的情况

✅ **你是业务用户，满足以下条件**:
- 关注业务细节多于技术细节
- 需要逐步理解方案
- 希望在每个阶段深度参与
- 愿意投入更多时间获得更好理解

✅ **你的问题特点**:
- 需求复杂，有较多不确定性
- 特殊领域或定制化程度高
- 需要多方协调和确认

⏱️ **时间投入**: 用户交互约30-40分钟，总计95-130分钟

## 💡 用户交互要点

### P0级交互（强制确认）

**必须确认的5个关键点**:

1. **Todo List** (Phase 0)
   - 这是"执行合同"
   - 系统会跟踪偏离
   - 建议: 仔细审阅，确保覆盖所有需求

2. **交互模式** (Phase 0.5)
   - 决定后续流程
   - 不可中途更改
   - 建议: 根据自己的背景和时间选择

3. **十要素模型** (Phase 1.5)
   - 统一真相源
   - 所有后续工作的基础
   - 建议:
     - 模式A: 逐个要素仔细审阅
     - 模式B: 确认框架后，Phase 2逐步完善

4. **技术方案** (Phase 3)
   - 代码生成的唯一依据
   - 方案确认后不可更改
   - 建议: 重点关注约束、目标、算法是否符合需求

5. **最终交付** (Phase 4)
   - 确认所有交付物
   - 标志项目完成
   - 建议: 审阅质量报告，确认无遗漏

### P1级交互（置信度低时触发）

**常见触发场景**:
- 需求描述模糊
- 存在多种可能的理解
- 缺少关键信息

**如何应对**:
- 认真回答澄清问题
- 提供尽可能详细的信息
- 如不确定，可以说"我需要时间确认"

### P2级交互（专家冲突时触发）

**常见冲突**:
- 算法选择冲突
- 约束与目标矛盾
- 领域实践与技术最优不一致

**如何仲裁**:
- 理解双方理由
- 考虑业务优先级
- 选择最符合你需求的方案
- 可以选择"混合"或"让我再想想"

## ❓ FAQ 常见问题

### Q1: 如果我中途需要暂停怎么办？

**A**: APS 模块支持断点恢复（V4.3）

```bash
# 暂停后，下次启动时
bmad aps

# 检查状态
*check-status

# 智能恢复
*resume
```

系统会从上次保存的Phase状态继续执行。

### Q2: 我可以修改已确认的内容吗？

**A**: 部分可以，但有限制

- ✅ **Phase 0-1**: 可以返回重新生成Todo
- ❌ **Phase 1.5**: 十要素模型确认后不可更改（需重新开始）
- ❌ **Phase 3**: 方案确认后不可更改（需重新开始Phase 3）
- ✅ **代码**: 可以手动修改生成的代码

**建议**: 在P0确认点仔细审阅，避免后续返工。

### Q3: 生成的代码可以直接运行吗？

**A**: 目标是92%可用率

- ✅ 大部分情况可以直接运行
- 🔧 可能需要微调：
  - 数据接口适配
  - 特定环境配置
  - 个性化调整

**建议**: 先在小规模数据上测试。

### Q4: 如果我的问题很特殊，系统处理不了怎么办？

**A**: 系统会输出"能力缺口报告"

```
📋 能力缺口报告

缺失知识: 特殊的多目标优化算法（NSGA-III）

已搜索路径:
- @专家库/算法库/meta-heuristic/*
- @专家库/目标库/multi-objective/*

建议解决方案:
1. 补充知识模块到专家库
2. 使用扩展指导智能体提取现有算法知识
3. 联系技术支持

系统已阻断执行，等待处理。
```

你可以：
1. 提供现有算法代码，使用扩展指导提取知识
2. 简化问题，使用现有知识库
3. 联系技术支持添加新知识模块

### Q5: 两种模式的输出结果有区别吗？

**A**: 没有质量区别，只有过程区别

- ✅ 最终方案质量: 相同
- ✅ 代码质量: 相同
- ✅ 交付物: 相同
- 🔄 过程: 不同（集中 vs 增量）
- ⏱️ 时间: 模式A更快

### Q6: 我可以跳过某些确认吗？

**A**: P0级确认不可跳过

- ❌ P0（5个关键点）: 强制确认
- ✅ P1（澄清问题）: 可以跳过，但可能影响质量
- ✅ P2（冲突仲裁）: 系统会采用默认策略

**建议**: 不要跳过任何确认，以确保结果符合预期。

### Q7: 质量门禁不通过怎么办？

**A**: 系统会自动修复（最多3次）

```
⚠️ 质量门禁2未通过: 逻辑验证失败

问题: 约束验证函数缺少边界条件检查

修复中... (第1次尝试)

✅ 修复完成，重新验证...
✅ 质量门禁2: PASS
```

如果3次修复仍失败，系统会：
1. 生成详细错误报告
2. 标记问题位置
3. 建议手动修复方向
