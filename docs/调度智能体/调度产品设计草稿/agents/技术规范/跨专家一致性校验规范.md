## 📋 文档概述

本规范定义了增量确认模式(模式B)中,各专家确认内容之间的一致性校验机制。在Phase 2.5阶段,系统将自动检测领域、约束、目标、算法四个专家的确认结果是否存在冲突或不一致,并触发相应的处理流程。

### 核心目标

1. **早期发现冲突**: 在方案生成前发现专家间的不一致
2. **降低返工成本**: 避免后期大规模调整
3. **提升方案质量**: 确保各专家配置协调一致
4. **用户参与决策**: 让用户在了解冲突影响后做出明智选择

---

## 🎯 一致性校验的必要性

### 问题场景

增量确认模式下,各专家独立与用户交互,可能出现以下问题:

| 问题类型            | 示例                                  | 影响                    |
| ------------------- | ------------------------------------- | ----------------------- |
| **领域-约束不一致** | 领域分析"时效性极高",但未设时间窗约束 | 方案无法体现业务优先级  |
| **约束-算法不匹配** | 10个硬约束 + 遗传算法                 | 算法难以找到可行解      |
| **目标-领域偏离**   | 领域强调成本,目标权重却是时间0.7      | 方案与业务目标背离      |
| **约束-目标重复**   | 时间窗软约束 + 时间目标               | 双重计数,过度强调某因素 |

### 校验时机

**Phase 2.5**: 所有专家增量确认完成后,方案集成前

```yaml
工作流程:
  Phase 2.1: 领域专家增量确认 ✅
  Phase 2.2: 约束专家增量确认 ✅
  Phase 2.3: 目标专家增量确认 ✅
  Phase 2.4: 算法专家增量确认 ✅

  Phase 2.5: 一致性校验 ← 当前阶段
    - 运行校验规则
    - 检测冲突
    - 如有冲突 → 触发 P2 仲裁
    - 无冲突 → 进入 Phase 3

  Phase 3: 方案集成
```

## 🔍 具体校验规则

### 类别1: 领域-约束一致性规则

#### 规则 DC-001: 时效性与时间窗约束对齐

```yaml
rule_id: 'DC-001'
name: '时效性与时间窗约束对齐'
category: 'Domain-Constraint'
experts_involved: ['domain-expert', 'constraint-expert']
severity: 'high'

condition:
  description: |
    领域专家确认时效性为"高"或"极高",
    但约束专家未建立时间窗约束
  logic: |
    domain.time_criticality in ["high", "extreme_high"] AND
    NOT exists(constraints where type == "time_window")

conflict_description: |
  领域分析指出时效性{domain.time_criticality},但未建立时间窗约束。
  这可能导致方案无法体现业务对时效性的要求。

impact_analysis: |
  - 方案可能允许任意延误,与业务预期不符
  - 客户满意度目标难以保障
  - 缺乏时效性的量化评估标准

recommendation: |
  建议:
  1. 约束专家增加时间窗约束 (软约束,允许适度违反)
  2. 或领域专家重新评估时效性等级
  3. 或在目标中强化时间相关目标权重

auto_fix:
  supported: false
  reason: '需要业务判断,无法自动修复'

examples:
  - scenario: '生鲜配送'
    trigger_data:
      domain: { time_criticality: 'extreme_high' }
      constraints: [{ type: 'capacity' }, { type: 'work_hours' }]
    expected_result: '触发警告,建议增加时间窗约束'
```

#### 规则 DC-002: 不确定性与鲁棒性约束对齐

```yaml
rule_id: 'DC-002'
name: '不确定性与鲁棒性约束对齐'
category: 'Domain-Constraint'
experts_involved: ['domain-expert', 'constraint-expert']
severity: 'medium'

condition:
  description: |
    领域专家确认存在"高"不确定性,
    但约束建模未考虑缓冲或鲁棒性机制
  logic: |
    domain.uncertainty_level == "high" AND
    NOT exists(constraints where has_buffer OR robustness_mechanism)

conflict_description: |
  领域分析存在高不确定性({domain.uncertainty_types}),
  但约束建模未包含缓冲或鲁棒性机制,可能导致方案脆弱。

impact_analysis: |
  - 方案对不确定性敏感,实际执行易失败
  - 需要频繁调整和人工干预
  - 客户满意度波动大

recommendation: |
  建议:
  1. 在时间相关约束中增加缓冲时间 (如+15%)
  2. 在容量约束中预留安全边际 (如-10%)
  3. 考虑使用鲁棒性优化算法

auto_fix:
  supported: true
  strategy: '在软约束的容忍度中自动增加15%缓冲'
  confidence: 0.7

examples:
  - scenario: '外卖配送,高峰期'
    trigger_data:
      domain: { uncertainty_level: 'high', uncertainty_types: ['demand', 'traffic'] }
      constraints: [{ name: '时间窗', tolerance: 0 }]
    expected_result: '建议增加时间缓冲'
```

#### 规则 DC-003: 规模与约束数量合理性

```yaml
rule_id: 'DC-003'
name: '规模与约束数量合理性'
category: 'Domain-Constraint'
experts_involved: ['domain-expert', 'constraint-expert']
severity: 'low'

condition:
  description: |
    问题规模较小,但约束数量过多,可能过度约束
  logic: |
    domain.scale in ["small", "very_small"] AND
    count(constraints where hardness == "hard") > 5

conflict_description: |
  问题规模为{domain.scale} ({domain.customer_count}客户),
  但设置了{hard_constraint_count}个硬约束,可能导致过度约束。

impact_analysis: |
  - 可能无可行解或解空间极小
  - 算法求解困难,运行时间长
  - 方案灵活性差

recommendation: |
  建议:
  1. 将部分硬约束放松为软约束
  2. 重新评估哪些约束是真正"必须"的
  3. 或确认问题规模是否被低估

auto_fix:
  supported: false
  reason: '需要业务判断'

examples:
  - scenario: '小规模调度'
    trigger_data:
      domain: { scale: 'small', customer_count: 10 }
      constraints: [8个硬约束]
    expected_result: '警告过度约束'
```

### 类别2: 约束-算法匹配规则

#### 规则 CA-001: 硬约束数量与算法能力匹配

```yaml
rule_id: 'CA-001'
name: '硬约束数量与算法能力匹配'
category: 'Constraint-Algorithm'
experts_involved: ['constraint-expert', 'algorithm-expert']
severity: 'high'

condition:
  description: |
    硬约束数量过多,但选择的算法约束处理能力弱
  logic: |
    count(constraints where hardness == "hard") > 8 AND
    algorithm.type in ["genetic", "simulated_annealing", "particle_swarm"]

conflict_description: |
  存在{hard_constraint_count}个硬约束,
  但选择的{algorithm.name}对硬约束处理能力有限,
  可能难以找到可行解。

impact_analysis: |
  - 算法可能长时间找不到可行解
  - 需要大量迭代或运行时间
  - 方案质量难以保证

recommendation: |
  建议:
  1. 将部分硬约束放松为高权重软约束
  2. 或选择约束处理能力更强的算法:
     - 约束规划 (Constraint Programming)
     - 分支定界 (Branch and Bound)
     - 混合算法 (GA + 局部搜索)

auto_fix:
  supported: false
  reason: '涉及核心算法选择,需用户决策'

examples:
  - scenario: '复杂VRP'
    trigger_data:
      constraints: [10个硬约束]
      algorithm: { type: 'genetic', name: '遗传算法' }
    expected_result: '警告算法能力不足'
```

#### 规则 CA-002: 问题规模与算法复杂度匹配

```yaml
rule_id: 'CA-002'
name: '问题规模与算法复杂度匹配'
category: 'Constraint-Algorithm'
experts_involved: ['domain-expert', 'algorithm-expert']
severity: 'medium'

condition:
  description: |
    问题规模很大,但选择了复杂度过高的算法
  logic: |
    domain.customer_count > 200 AND
    algorithm.complexity in ["exponential", "factorial"]

conflict_description: |
  问题规模为{domain.customer_count}客户,
  但选择的{algorithm.name}复杂度为{algorithm.complexity},
  运行时间可能无法接受。

impact_analysis: |
  - 算法运行时间可能超过数小时甚至数天
  - 无法满足实时或准实时需求
  - 资源消耗巨大

recommendation: |
  建议:
  1. 选择复杂度更低的启发式或元启发式算法
  2. 或采用分治策略,将问题分解为子问题
  3. 或接受近优解,不追求精确最优

auto_fix:
  supported: true
  strategy: '推荐复杂度适配的算法列表'
  confidence: 0.8

examples:
  - scenario: '大规模VRP'
    trigger_data:
      domain: { customer_count: 500 }
      algorithm: { type: 'exact', complexity: 'exponential' }
    expected_result: '建议改用元启发式算法'
```

#### 规则 CA-003: 时效性要求与算法终止条件匹配

```yaml
rule_id: 'CA-003'

  - 无法支持实时调度场景
  - 用户体验差

recommendation: |
  建议:
  1. 缩短算法最大运行时间 (如5分钟内)
  2. 或调整算法参数,加速收敛
  3. 或接受较低的解质量要求

auto_fix:
  supported: true
  strategy: '根据时效性自动调整max_time: 极高→300秒, 高→600秒'
  confidence: 0.75

examples:
  - scenario: '实时调度'
    trigger_data:
      domain: { time_criticality: 'extreme_high' }
      algorithm: { max_time: 900 }
    expected_result: '建议缩短运行时间'

auto_fix:
  supported: true

examples:

### 类别4: 目标-约束协调规则

#### 规则 OC-001: 软约束惩罚与目标重复检测

rule_id: 'OC-001'
name: '软约束惩罚与目标重复检测'

  2. 或将软约束改为硬约束,仅在目标中优化时间

auto_fix:
  supported: false
  reason: '需要权衡业务语义'

examples:
  - scenario: 'VRP with time windows'
    trigger_data:
      constraints: [{ name: '时间窗', hardness: 'soft', penalty: '时间延误×100' }]

```

## 💻 校验引擎设计

### 核心组件

```python
class ConsistencyValidator:
    """一致性校验器"""

    def __init__(self):
        self.rules = self._load_rules()
        self.conflict_resolver = ConflictResolver()

    def _load_rules(self) -> List[ValidationRule]:
        """加载所有校验规则"""
        return [
            # 领域-约束规则
            DC001_TimelinessAlignment(),
            DC002_UncertaintyRobustness(),
            DC003_ScaleConstraintBalance(),

            # 约束-算法规则
            CA001_HardConstraintAlgorithmMatch(),
            CA002_ScaleAlgorithmComplexity(),
            CA003_TimelinessAlgorithmSpeed(),

            # 目标-领域规则
            OD001_ObjectiveWeightPriorityAlign(),
            OD002_TimelinessTimeObjectiveAlign(),

            # 目标-约束规则
            OC001_SoftConstraintObjectiveDuplicate(),
            OC002_TargetValueFeasibility(),

            # 完整性规则
            CE001_RequiredFieldsCompleteness(),
        ]

    def validate(
        self,
        domain_results: dict,
        constraint_results: dict,
        objective_results: dict,
        algorithm_results: dict
    ) -> ValidationReport:
        """
        执行完整的一致性校验

        Returns:
            ValidationReport: 包含所有冲突和建议
        """
        confirmed_data = {
            "domain": domain_results,
            "constraint": constraint_results,
            "objective": objective_results,
            "algorithm": algorithm_results
        }

        conflicts = []

        # 逐条运行校验规则
        for rule in self.rules:
            if rule.is_applicable(confirmed_data):
                conflict = rule.check(confirmed_data)
                if conflict:
                    conflicts.append(conflict)

        # 生成校验报告
        report = ValidationReport(
            total_rules_checked=len(self.rules),
            conflicts=conflicts,
            severity_distribution=self._count_severity(conflicts),
            has_blocking_issues=any(c.severity == "high" for c in conflicts)
        )

        return report

    def _count_severity(self, conflicts: List[Conflict]) -> dict:
        """统计冲突严重等级分布"""
        return {
            "high": sum(1 for c in conflicts if c.severity == "high"),
            "medium": sum(1 for c in conflicts if c.severity == "medium"),
            "low": sum(1 for c in conflicts if c.severity == "low")
        }
```

### 规则基类

```python
class ValidationRule(ABC):
    """校验规则基类"""

    def __init__(self):
        self.rule_id = None
        self.name = None
        self.category = None
        self.severity = None
        self.experts_involved = []

    @abstractmethod
    def is_applicable(self, confirmed_data: dict) -> bool:
        """判断规则是否适用于当前数据"""
        pass

    @abstractmethod
    def check(self, confirmed_data: dict) -> Optional[Conflict]:
        """
        执行规则检查

        Returns:
            Conflict: 如果发现冲突,返回冲突对象;否则返回None
        """
        pass

    def generate_recommendation(self, conflict_data: dict) -> str:
        """生成调整建议"""
        pass
```

class DC001_TimelinessAlignment(ValidationRule):
    """DC-001: 时效性与时间窗约束对齐"""

    def __init__(self):
        super().__init__()
        self.rule_id = "DC-001"
        self.name = "时效性与时间窗约束对齐"
        self.category = "Domain-Constraint"
        self.severity = "high"
        self.experts_involved = ["domain-expert", "constraint-expert"]

    def is_applicable(self, confirmed_data: dict) -> bool:
        """当领域时效性为高或极高时适用"""
        domain = confirmed_data.get("domain", {})
        return domain.get("time_criticality") in ["high", "extreme_high"]

    def check(self, confirmed_data: dict) -> Optional[Conflict]:
        """检查是否存在时间窗约束"""
        domain = confirmed_data["domain"]
        constraints = confirmed_data["constraint"].get("constraints", [])

        # 检查是否有时间窗约束
        has_time_window = any(
            c.get("type") == "time_window" or
            c.get("category") == "时间约束"
            for c in constraints
        )

        if not has_time_window:
            return Conflict(
                rule_id=self.rule_id,
                name=self.name,
                severity=self.severity,
                experts_involved=self.experts_involved,
                description=f"领域分析指出时效性{domain['time_criticality']},但未建立时间窗约束",
                impact="方案可能允许任意延误,与业务预期不符",
                recommendation=self._generate_recommendation(domain, constraints),
                auto_fix_available=False
            )

        return None

    def _generate_recommendation(self, domain: dict, constraints: list) -> str:
        """生成建议"""
        return f"""
建议:
1. 约束专家增加时间窗约束 (软约束,允许适度违反)
2. 或领域专家重新评估时效性等级 (当前: {domain['time_criticality']})

        """.strip()

### 冲突对象定义

```python
@dataclass
class Conflict:
    """冲突对象"""
    rule_id: str
    name: str
    severity: str  # high, medium, low
    experts_involved: List[str]
    description: str
    impact: str
    recommendation: str
    auto_fix_available: bool
    auto_fix_strategy: Optional[str] = None
    auto_fix_confidence: Optional[float] = None

    def to_user_prompt(self) -> str:
        """生成用户友好的提示"""
        severity_emoji = {
            "high": "🔴",
            "medium": "🟠",
            "low": "🟡"
        }

        prompt = f"""
{severity_emoji[self.severity]} **【{self.severity.upper()}】{self.name}**

**问题描述**:
{self.description}

**影响分析**:
{self.impact}

**调整建议**:
{self.recommendation}
        """.strip()

        if self.auto_fix_available:
            prompt += f"\n\n💡 **自动修复**: 支持 (置信度: {self.auto_fix_confidence:.0%})\n{self.auto_fix_strategy}"

        return prompt
```

## 🔄 冲突解决流程

### 交互流程

```yaml
冲突解决流程:
  步骤1: 检测冲突
    - 运行所有校验规则
    - 生成 ValidationReport

  步骤2: 呈现冲突
    - 按严重等级排序
    - 使用 BMAD numbered options (1-9) 格式
    - 提供清晰的影响分析和建议

  步骤3: 用户决策
    选项1: 接受 → 进入下一阶段 (记录风险)
    选项2-3: 调整 → 回到对应专家重新确认
    选项4: 自动修复 → 应用系统建议
    选项5-7: 查看分析 → 提供更多信息
    选项8: 重审 → 重新开始增量确认
    选项9: 其他 → 开放式反馈

  步骤4: 应用调整
    - 如果用户选择调整,回到对应专家
    - 重新确认冲突相关的配置项
    - 再次运行一致性校验

  步骤5: 验证解决
    - 所有冲突解决后,进入 Phase 3
    - 如仍有冲突,重复步骤2-4
```

### 规则扩展

添加新规则的步骤:

1. **定义规则规范** (YAML 格式)
2. **实现规则类** (继承 ValidationRule)
3. **编写单元测试**
4. **注册到校验器** (在 \_load_rules 中添加)
5. **更新文档** (记录新规则)

### 规则优先级

当多个规则冲突时:

1. 高严重等级优先
2. 涉及专家数多的优先
3. 影响范围大的优先
